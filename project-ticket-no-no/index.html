section01

핵심 변화:
Ticket-driven → Outcome /
Project-driven

전통적인 Jira식 조직은 대략 이렇습니다.

01PM이 요구사항 정의
02기획자가 User Story 작성
03개발 Task로 잘게 분해
04Story point 추정 → Sprint → 담당자 Assign
05개발자는 자기 Ticket 처리 → Done → 다음 Ticket

이 구조에서 개발자의 사고 범위가 자연스럽게 “이 제품을 어떻게 성공시킬까?”가 아니라 “내 티켓을 어떻게 완료할까?”가 됩니다.

조직이 수동적으로 변하는 문제의 본질도 여기 있습니다.

반면 최신 방식은 이런 형태에 훨씬 가깝습니다.

01Goal / Problem
02Project / Bet
03소수의 Cross-functional Team에 프로젝트 자체를 맡김
04팀이 솔루션·구현방법·작업분해를 스스로 결정
05필요할 때 Issue 생성 → Design / Code / PR / Deploy → 실제 사용자 반응

즉 Task를 assign하는 게 아니라 Problem 또는 Project를 assign합니다.

section02

이걸 가장 노골적으로 주장하는 곳이
Basecamp의 Shape Up입니다

Assign projects, not tasks.

Basecamp는 아예 챕터 제목부터 “Assign projects, not tasks”입니다.

그리고 명시적으로 관리자가 프로젝트를 미리 Task로 잘게 쪼개 다른 사람에게 실행시키는 역할을 하지 않는다고 설명합니다. 팀에게 전체 프로젝트를 넘기고, 팀이 자기 task와 접근방법을 직접 정의하게 합니다. 이유도 동일합니다. 일을 사전에 잘게 쪼개면 각 사람은 전체 제품이 아니라 자기 조각만 보게 되고, 실행자가 전체 결과에 대한 판단을 하지 않게 된다는 겁니다.

그리고 Basecamp는 backlog 자체에도 상당히 부정적입니다. 수백 개의 과거 요구사항을 계속 grooming하고 우선순위를 관리하는 행위가 실제 제품을 만드는 시간을 잡아먹는다고 보고, “Bets, not backlogs”를 사용합니다.

section03

Linear는 더 직접적입니다:
“User Story는 anti-pattern”

요즘 OpenAI, Cursor, Ramp, Vercel, Perplexity 같은 고속 제품회사들이 많이 사용하는 Linear의 내부 방식도 흥미롭습니다.

Linear는 공식 Method 문서에서 아예 User Story를 anti-pattern이라고 규정합니다.

이유 중 하나가 User Story가 엔지니어를 기계적으로 요구사항을 코딩하는 역할로 고립시킬 수 있기 때문이라고 설명합니다.

Everyone writes their own issues.

즉 PM/기획자가 개발자의 작업 Ticket을 대신 설계하지 않습니다.

프로젝트 차원에서 사용자 문제와 UX와 목표를 충분히 이해시킨 뒤, 실제 일을 하는 사람이 필요에 따라 자기 Issue를 씁니다.

section04

그런데 재미있는 사실:
OpenAI도 Issue Tracker를 엄청 씁니다

여기서 굉장히 중요한 반전이 있습니다.

티켓 자체가 나쁜 것은 아닙니다.

OpenAI는 Linear를 조직적으로 광범위하게 사용하고 있고, Linear 측 사례에 따르면 3,000명 이상 규모로 확장해서 사용하고 있습니다. Cursor도 Linear를 사용하고, Ramp도 전사 제품 워크플로를 Linear에 연결해 사용합니다.

따라서 “최신 회사들은 티켓을 안 쓴다.”는 사실이 아닙니다. 오히려 엄청 많이 씁니다.

다만 티켓의 의미가 다릅니다.

옛날

Ticket = 상사가 나에게 시킨 일

최신

Issue = 우리가 발견한 일을 기록하는 Context Object

이 차이가 엄청 큽니다.

section05

특히 2026년에
이게 한 단계 더 변하고 있습니다

Linear가 2026년 3월에 발표한 문구가 꽤 상징적입니다.

“Issue tracking is dead.”

물론 Linear라는 판매회사의 마케팅 문구이기 때문에 그대로 받아들일 필요는 없습니다. 그런데 내용을 보면 주장하는 바는 명확합니다.

01PM이 일을 정의
02엔지니어에게 나중에 전달
03workflow / prioritization / negotiation / status 관리

기존 Issue Tracking 시스템은 이런 handoff 구조를 전제로 만들어졌다는 겁니다.

AI agent 시대에는 planning → implementation → review 사이의 절차 자체가 압축되고 있기 때문에 사람이 해야 할 핵심은 intent, judgment, taste로 이동한다고 주장합니다.

section06

Coinbase는 2026년에
이걸 꽤 극단적으로 실험하고 있습니다

Coinbase의 Base 조직은 2026년 초 엔지니어들에게 한동안 IDE 없이 agent 중심으로 개발하게 하는 실험까지 했습니다.

중요한 건 Linear를 없앤 게 아니라 오히려 Linear를 조직의 Context / Source of Truth로 만들었다는 점입니다.

제품 요구사항, 디자인, 버그, 프로젝트 상태 등의 맥락을 거기에 두고,

inputSlack
contextLinear Issue 자동 생성
agentAgent가 분석
build코드 작성
artifactPR 생성
humanEngineer Review

즉 사람이 하루 종일 TODO → IN PROGRESS → CODE REVIEW → QA → DONE 카드를 옮기는 게 아닙니다.

시스템과 agent가 workflow를 관리하고, 사람은 판단을 합니다.

이게 꽤 중요한 2026년의 변화입니다.

section07

Ramp는
더 극단적입니다

Ramp의 내부 coding agent인 Inspect는 Linear에 존재하는 spec, 고객 피드백, 코드 context 등을 이용합니다.

Linear가 공개한 Ramp 사례에 따르면 현재 merged PR의 60% 이상을 내부 agent가 작성합니다.

그래서 미래의 Issue Tracker는 사람을 관리하는 시스템에서 사람 + Agent가 공유하는 Context Graph 쪽으로 가고 있습니다.

이 관점으로 보면 Jira의 복잡한 workflow/status/field가 점점 낡아 보이는 이유도 설명됩니다.

section08

Figma도 조직철학이
상당히 비슷합니다

Figma CTO가 설명한 제품개발 방식에서도 전통적인 PM → Design → Engineering linear waterfall을 부정합니다.

엔지니어도 how뿐 아니라 what을 함께 결정하고, 프로젝트 초기의 concept document 단계부터 엔지니어·디자이너·PM이 같이 들어갑니다.

Engineering Critique도 흥미로운데, Figma는 이것을 approval process가 아니라고 명시합니다. 목적은 승인받는 것이 아니라 다른 전문가로부터 빨리 feedback을 얻는 것입니다.

2025년 Figma가 1,199명의 product builder를 조사한 연구에서도 역할 경계가 빠르게 흐려지고 있었습니다. 응답자의 64%가 두 개 이상의 역할을 수행한다고 답했고, 제품개발 과정에서 PM·개발·디자인 간 업무 중첩이 증가하고 있었습니다.

2026년 연구에서는 이 현상이 AI로 더 강해졌습니다. 개발자가 디자인에 참여하는 비율, 디자이너가 개발에 참여하는 비율 모두 크게 증가했습니다.

즉, “기획자가 생각 → 디자이너가 그림 → 개발자가 구현”이라는 공장식 분업 자체가 흐려지고 있습니다.

section09

연구적으로도
autonomy 쪽이 맞습니다

이건 단순한 Silicon Valley 유행만은 아닙니다.

Google DORA 연구에서 지속적으로 높은 성과와 연결되는 조직 특성 중 하나가 loosely coupled autonomous teams입니다.

좋은 팀은 외부 승인을 계속 받지 않고,

  • 설계를 바꿀 수 있고
  • 다른 팀의 세밀한 coordination 없이 일할 수 있고
  • 독립적으로 테스트하고
  • 독립적으로 deploy할 수 있어야 합니다.

특히 DORA의 Team experimentation 항목은 더 직접적입니다.

높은 성과와 연결되는 능력으로

  • 새로운 아이디어를 외부 허가 없이 실험
  • 개발 중 specification 수정
  • story/spec을 외부 승인 없이 변경

그러니까 연구가 지지하는 건 Jira 사용 여부가 아니라 local decision authority입니다.

conclusionC

그래서 제가 내린 결론

싫어해야 할 대상은 사실 Jira가 아닙니다. 정확하게는 이것입니다.

Ticket Factory

어떤 사람이 생각하고
다른 사람이 잘게 쪼개고
또 다른 사람이 시키고
개발자는 실행하고
PM은 상태를 체크하고
관리자는 throughput을 보는 조직.

이 구조가 사람을 수동적으로 만듭니다.

그리고 Jira는 이 구조를 만들기가 너무 쉬운 도구인 것은 맞습니다.

하지만 Linear를 가져다 놓고 똑같이 PM이 100개 Issue 생성 → 개발자 Assign → 매일 상태 확인하면 Linear로 만든 Jira 조직일 뿐입니다.

기획팀이 개발팀에
Task를 Hand-off하면 안 됩니다.

과거의 Agile은 “일을 잘게 쪼개서 사람을 관리”했고, 최신 고성과 제품조직은 “문제를 명확히 정의해서 유능한 팀에 맡기는” 방향으로 이동하고 있습니다.

Ticket은 없어지는 것이 아니라, ‘명령서’에서 ‘맥락과 실행 기록’으로 격하되고 있습니다.

2026년 AI Agent가 들어오면서 이 변화가 더 빨라지고 있습니다. Atlassian 자신이 3,500명의 개발자·관리자를 조사한 2025 Developer Experience 보고서에서도 AI로 개인 생산성은 올라가는데 조직적 비효율은 오히려 증가하고 있다고 보고했습니다. 코드 생산속도보다 조직운영 방식이 병목이 된다는 얘기입니다.
